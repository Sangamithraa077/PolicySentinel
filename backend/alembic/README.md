# alembic/ — Database Migrations

Alembic owns the PostgreSQL schema going forward: every table, enum type,
constraint, index, and trigger lives in a versioned migration under
`versions/`, starting from `versions/*_initial_schema.py`, which brings an
empty database up to parity with the ORM models in `models/`.

## Running migrations

Migrations read `DATABASE_URL` from the same `Settings` the app uses
(`config/settings.py`, sourced from the environment / `.env`) — there is
no separate connection string to keep in sync.

```bash
# from backend/, with the venv from requirements.txt active
alembic upgrade head        # apply all pending migrations
alembic downgrade -1        # roll back one migration
alembic current             # what's applied to this database
alembic history             # full migration chain
alembic revision --autogenerate -m "add x to y"   # generate a new migration from model changes
```

Always read an autogenerated migration before running it — Alembic diffs
`models/` against the live schema well for columns and simple indexes, but
does not detect CHECK constraint changes, and knows nothing about the
plpgsql trigger functions in the initial migration (`set_updated_at`,
`prevent_mutation`) or the triggers built from them; those must be edited
by hand when they change.

## Relationship to `docker/postgres/init/`

`docker/postgres/init/001_schema.sql` only bootstraps the `pgcrypto` and
`citext` extensions (they need to exist before any migration's DDL runs,
and creating them there — as well as idempotently inside the initial
migration itself — means `alembic upgrade head` also works standalone
against a plain empty Postgres, e.g. in CI, without that init script).
It does **not** create tables, types, or indexes — that would double up
with the migrations here and fail on a second run. If you find yourself
tempted to add a table to `001_schema.sql`, write a migration instead.

## Circular foreign key

`policies.current_version_id` and `policy_versions.policy_id` reference
each other. The initial migration creates `policies` first with
`current_version_id` as a plain column, creates `policy_versions`, then
adds `policies_current_version_fk` via a separate `op.create_foreign_key`
call. `downgrade()` must drop that constraint *before* dropping either
table, or the `DROP TABLE` will fail on the dangling reference.
